### MR-M1: sender domain label crashes the dashboard (Medium)
- **Path.** `brandForDomain` checked each label of the sender's domain with `in` against plain objects. `in` also
  matches inherited members, so for `constructor` it returned the `Object` function. `Brand` then read `.title` from
  `undefined` and threw. There is no `error.tsx` anywhere under `src/app`. The pages that render `SenderMark` are:
  - the dashboard's Needed list, which holds Run, Undo, the key card and Disconnect (up to 14 days);
  - search results;
  - run receipts and the batch audit.
- **Exploit.** Send any Mailroom user mail from `m@constructor.<a domain you control>`.
- **Observed locally.** `brandForDomain("constructor.example.com")` returned `[Function Object]`, and rendering
  `SenderMark` threw `TypeError: Cannot read properties of undefined (reading 'title')`.
- **Fix.** Own-key lookups (`Object.hasOwn`). The sender renders as initials, and known brands are unchanged.
- **Test.** `tests/sender-mark.test.ts`.

## Fixed defensively (lead still needs a Gmail check)
**Sender domains reached Gmail trash queries unquoted.** `domainOf` took the *first* `<…>` in a From header, including
one inside the quoted display name, and didn't validate it.
- **Example.** `"Deals <x@{evil.example bank.example}>" <news@evil.example>` became the "domain"
  `{evil.example bank.example}`.
- **Where it went.** A sender decision (trash, trash-old, protect, work, family, heavy promo) put it straight into
  Gmail searches: `from:${domain} older_than:…`, the `-from:(a OR b)` people guard, and the sender-list routes.
- **Why it matters.** If Gmail reads `from:{a b}` as OR, choosing "trash" for that spammy sender also trashes
  `bank.example`'s mail. A crafted protected entry could also break out of the people guard.
- **Fix.**
  - The address is now the last `<…>`, and only a hostname counts as a domain.
  - `/api/senders/decide` answers 400 for anything else.
  - Rules and routes drop stored entries with whitespace, quotes, braces or parentheses (`querySafeSender`).
- **What users see.** Nothing changes for real senders: real domains are hostnames.
- **Test.** `tests/sender-domain.test.ts`.
- **Still to check.** How Gmail search reads `from:{a b}`. Verify it in a throwaway Gmail account.

## Low / hardening notes (not fixed)
- **Trash without the guards.** The immediate trash in `/api/senders/decide` skips the protected-category, protected
  people and `-in:sent` guards that daily rules use. Undoing it leaves the standing rule in place.
- **System labels.** The manual `label` action accepts `TRASH` and `SPAM`. It's self-only, but it bypasses the action
  allowlist.
- **Search on page load.** `/app/search?q=` runs on load, so a cross-site link spends a signed-in user's TypeSafe key.
  For Kevin that's the house key. Require a submit.
- **Middleware.**
  - Lets non-GET requests without `Origin` through and compares host, not scheme. Add a `Sec-Fetch-Site` check.
  - The exemption uses `startsWith('/api/auth')`; make it `/api/auth/`.
- **Cron and disconnect.**
  - The cron compares its secret with `!==`, and reads the due list once without re-checking `scheduleEnabled`.
  - Token revocation ignores Google's status and sends the token in the URL. Disconnect leaves Mailroom's Gmail
    filters running.
- **Thread facts (critic).** `threads.ts` `addressOf` has the same first-`<…>` bug, so a display name can make a
  message count as "sent by me". That gates Action Needed and the needs-reply filters. Use the last `<…>`.
- **Cookies.**
  - Auth.js cookies use `__Secure-`, not `__Host-`.
  - `trustHost: true` without a pinned `AUTH_URL`.
  - The house key trusts the Google email without `email_verified`. Bind the owner to the Google `sub` instead.
- **TypeSafe key fallback.** The SDK falls back to `TYPESAFE_API_KEY` when `apiKey` is undefined. Rename the house-key
  variable so a future code path can't bill it by accident.
- **Seed script.** `scripts/seed-preview-user.ts` commits a fixed session token for a preview user. Never run it
  against production.
- **Small bugs.**
  - `decryptSecret` doesn't pin the tag length or bind AAD.
  - Undo isn't atomic (self-only).
  - `senders/scan` clamps with `Math.min` only.
  - Gmail paths don't URL-encode ids.
- **Dev-only advisories.** The vite, vitest, esbuild and braces advisories don't ship.

## Checked and clean
- **Isolation.** Every route checks the session and keys its queries on the user's id. Run, batch, undo, restore and
  audit look up the run by id plus user, and each batch must belong to its run. Message ids from the client only reach
  the caller's own Gmail.
- **CSRF.** The Origin check refuses foreign, `null` and malformed origins. The session cookie is SameSite=Lax, all
  GETs are read-only, and `/api/auth` and `/api/cron` carry their own CSRF token or bearer secret.
- **Sign-in.** Same-email linking is refused. Login CSRF is blocked by PKCE, Auth.js's token and the server-action
  origin check. Redirects stay on-site. The scope check runs before any token is written, and sessions are deleted on
  disconnect.
- **The model.** Jev only labels, archives (above threshold, automated categories) or flags the message it judged. It
  never trashes, and code acts on its numeric scores only. Grading and rerank don't change the mailbox.
- **Filters and inputs.** Mailroom never creates a forward action. Message ids go in request bodies, capped at 5,000.
- **Rendering.** No HTML or script sink takes sender data. List-Unsubscribe links must be http(s), and no image loads
  from sender URLs. Framing is denied, and the CSP is strict apart from `'unsafe-inline'` scripts.
- **Secrets.** Tokens use AES-256-GCM with a random nonce and authenticated decrypt. The house key reaches the owner
  only, on every path. No keys or tokens appear in responses or logs.

## Not checked
- **Live behaviour.** Gmail's query parsing, Google consent settings, Vercel limits and Firewall rules, and the
  Neon data were not checked. The skill forbids probing deployments.
- **Execution.** Hunters and verifiers worked from source only. The parent ran the regression tests in a sandbox that
  blocks network access and limits CPU, file size and environment variables. It couldn't limit memory or process
  count, and the code wasn't mounted read-only. No browser run.
- **Critic gaps, deferred by the quick profile.**
  - The thread "from me" facts (above).
  - There are no per-user rate or concurrency limits on the 300 s routes (`/api/run`, scan, reconcile, undo), and no
    cap on saved searches, snapshots or dry-run receipts. Open sign-up can use up the 100-user Google cap.
